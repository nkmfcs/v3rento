# Rento — «Костюмерная»

SaaS для прокатов карнавальных костюмов. Мультитенантный: один сервер обслуживает
много независимых прокатов, которые **не видят данные друг друга** (изоляция на
уровне PostgreSQL, см. [Изоляция тенантов](#изоляция-тенантов-rls)).

**Репозиторий:** https://github.com/nkmfcs/v3.rento  
**Стек:** vanilla JS (без сборки) · Express 5 · PostgreSQL · деплой на Railway

---

## Быстрый старт

```bash
git clone https://github.com/nkmfcs/v3.rento.git
cd v3.rento
npm install

cp .env.example .env.local   # заполнить AUTH_SECRET и DATABASE_URL
npm run db:reset             # схема в чистую БД (ВНИМАНИЕ: дропает public)
npm run dev                  # http://localhost:3000
```

Нужен Node.js ≥ 18. Сборки нет — фронт отдаётся как статика, правки видны после
перезагрузки страницы.

> **Про `npm test`:** по умолчанию тесты бьют в **прод** и создают там реальных
> тенантов. Всегда запускайте против локального сервера:
> `TEST_BASE_URL=http://localhost:3000 npm test`

### Два фронта, общий бэкенд

Десктоп (`index.html` + `js/pc.js`) и мобайл (`m/index.html` + `js/mobile.js`) —
разные интерфейсы поверх одного API. Общее вынесено в `js/api.js` и `js/util.js`,
которые грузят **оба**.

> ⚠️ **Кэш-бастинг.** Все `<script>`/`<link>` подключаются с `?v=N`. При правке
> любого файла поднимайте версию — иначе браузер отдаст старый из кэша. Если
> правите **общий** файл (`api.js`, `util.js`, `art.js`, `ui.js`, `tokens.css`) —
> версию надо поднять **в обоих** HTML: `index.html` и `m/index.html`.

## Изоляция тенантов (RLS)

Ключевая часть системы. Изоляция держится не на дисциплине кода, а на
**Row-Level Security в самой БД**: даже если в запросе забыть `WHERE tenant_id`,
чужие строки не вернутся (fail-closed — без контекста видно 0 строк).

Как это работает: на каждый авторизованный запрос `db.js` закрепляет одно
соединение (`AsyncLocalStorage`), ставит `app.tenant_id` и делает `SET ROLE app_rls`.
Политики описаны в `db/migration-v7-rls.sql`, роль — в `v8`.

**Две ловушки, на которые легко наступить снова** (обе найдены эмпирически,
подробный разбор — [`docs/session-log-2026-07-13.md`](docs/session-log-2026-07-13.md), раздел 6):

1. **Пул Neon (pgbouncer, transaction mode) не держит сессионные переменные.**
   Через пул `app.tenant_id` протекал между соединениями — RLS не работал бы.
   Поэтому `db.js` подключается к **прямому** эндпоинту (убирает `-pooler.` из хоста).
2. **Роль `neondb_owner` имеет `BYPASSRLS`** — политики её не касаются, и снять
   атрибут нельзя. Поэтому приложение работает под отдельной ролью `app_rls`.

Скрипты обслуживания (`run-sql.mjs`, чистка тенантов) ходят под `neondb_owner`
с bypass — это нормально для миграций, но значит, что **проверять изоляцию
скриптами нельзя**, только через приложение.

Аварийный откат: `node scripts/run-sql.mjs db/migration-v7-rls-rollback.sql`

## Деплой

Railway следит за веткой `main` — **пуш в `main` = деплой в прод**. Отдельного
шага сборки нет.

```bash
git push origin main    # → Railway задеплоит автоматически
```

Переменные окружения задаются в панели Railway (не в файле). После выката
проверяйте прод с жёсткой перезагрузкой (Ctrl+Shift+R), иначе браузер может
держать старые ассеты.

**Порядок при изменении БД:** сначала выкатить код, который умеет работать и со
старой, и с новой схемой → проверить → применить миграцию → проверить снова.

## Как здесь принято работать

Выжимка из [`docs/session-log-2026-07-13.md`](docs/session-log-2026-07-13.md) —
методология, которая уже спасала от повторных багов:

1. **Сначала читать код, потом править** — не по памяти.
2. После правки JS — `node --check <файл>` (ловит синтаксис).
3. Поднять `?v=N` (см. предупреждение о кэше выше).
4. Коммит + пуш → Railway деплоит.
5. **Проверять вживую** на проде: логин в тестовый аккаунт, прогон сценария.
   Скриншоты в некоторых окружениях подвисают — надёжнее читать DOM и
   вычисленные стили через консоль.

Полезные детали:
- Мобильный редирект срабатывает при `innerWidth < 820`. Чтобы принудительно
  открыть десктоп — добавьте `?pc=1` к URL.
- Демо-тенант `karnaval` — **осознанная витрина**: на нём статичная разметка из
  HTML не заменяется реальными данными. Для всех остальных прокатов любой блок
  обязан либо рендериться из API, либо иметь пустое состояние. Если увидите
  «Шохрух», «Малика К.» или «12,4 млн» на реальном аккаунте — это утечка макета.

## Что в бэклоге

- **Ускорение загрузки** — `loadMe`/`loadAll` уже параллелятся; следующий шаг —
  единый `/bootstrap` (me + все данные одним запросом).
- **C2** — один адаптивный интерфейс вместо двух (удалить `/m`). Снимет целый
  класс багов «поправил на десктопе, забыл на мобайле».
- **Фичи** — фото костюмов, защита от двойных броней в календаре, экспорт,
  десктопный модуль «Расходы/зарплаты».
- **Интеграции** — Яндекс Delivery (сначала проверить доступность API в UZ),
  Telegram-бот, онлайн-оплаты (Payme/Click/Uzum), печать договора/чека.
- **Безопасность** — CSP без `unsafe-inline`, аудит-лог, 2FA/PIN, rate-limit
  по пользователю, бэкапы БД.
- **Штраф за просрочку** — отложен решением владельца (формула затрагивает
  реальные деньги клиента и неоднозначна).
