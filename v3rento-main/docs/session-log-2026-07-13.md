## 2. Пойманный баг: TDZ ломал загрузку десктопа

**Что случилось.** Добавляя авто-расчёт залога, я стал читать `settingsState` в
`pnoRenderSummary()`, а эта функция вызывается при загрузке модуля — раньше объявления
`let settingsState` (оно стояло ниже). Temporal Dead Zone → инициализация `pc.js` падала
целиком. Десктоп был сломан ~10 минут (версия v58).

**Как нашёл.** При проверке вживую `javascript_tool` вернул
`ReferenceError: Cannot access 'settingsState' before initialization`.

**Фикс.** Перенёс объявление `let settingsState={}` в начало файла. Урок: `const`/`let`,
которые читаются на этапе загрузки модуля, нельзя объявлять ниже точки использования.

## 3. Раздел A — бизнес-логика (было разорвано, стало работает)

Нашёл при аудите: **модуль «Деньги» и «Клиенты» работали наполовину.**

### 3.1 Заказы не были связаны с финансами
- **Было:** смена статуса/оплата заказа не создавала ни одной транзакции. «Деньги»
  показывали только то, что внесли вручную.
- **Стало:** при оплате/создании оплаченного заказа пишется `income`-транзакция
  (категория «Прокат», привязка `order_id`/`client_id`).

### 3.2 Приём оплаты (полная и частичная)
- **Было:** флаг `paid` ставился только при создании; изменить потом нельзя.
- **Стало:** миграция `orders.paid_amount` (v6), эндпоинт `POST /orders/:id/payment`,
  кнопка «Принять оплату» на десктопе и мобайле, бейдж «Оплачено X из Y», защита от
  переплаты.
- **Проверка:** заказ 300k → частичная 100k (долг 200k) → доплата (paid, долг 0);
  переплата отклонена. Income появляется в «Деньгах». Оба фронта.

### 3.3 Долг клиента
- **Было:** `clients.debt` никогда не писался → всегда 0.
- **Стало:** `recalcClient` считает `debt = Σ(total − paid_amount)` по выданным/
  просроченным/закрытым заказам.

### 3.4 Авто-депозит из настроек
- **Было:** залог в форме заказа зашит 150000.
- **Стало:** авто = `deposit_pct`% от стоимости проката, пересчёт при смене костюмов/дат,
  ручное переопределение отключает авто. Бэкенд подставляет из настроек, если API не прислал.

### 3.5 Штраф за просрочку
- **Решение владельца: пока без штрафов.** Формула касается реальных денег клиента и
  двусмысленна (% от чего в день) — не стал угадывать. Отложено.

### 3.6 Генерация уведомлений
- **Было:** таблица `notifications` никем не заполнялась → колокольчик всегда пуст.
- **Стало:** `server/notify.js`:
  - Событийные: новый заказ 📥, оплата 💰 (в обработчиках заказа).
  - Напоминания: просрочка ⚠️, возврат сегодня ⏰ — лениво при загрузке ленты, с

- **Проверка:** создан заказ → 📥; заказ с прошедшей датой → статус `over` + ⚠️;

## 5. Мигание демо-макета при загрузке

**Проблема (репорт владельца):** при открытии сайта сначала видны данные-макет
(«Карнавал»), через ~3с подменяются на реальные.

**Причина:** HTML отдаётся с зашитыми демо-значениями (витрина демо-тенанта), браузер
рисует их сразу, реальные данные приезжают после запросов к API.

**Фикс:** загрузочный гейт. `<html class="app-loading">` скрывает `body` и показывает
спиннер на фирменном фоне (псевдоэлементы на `<html>`). `init` снимает класс в `finally`.
В `<head>` — страховка по таймауту 8с (если JS упадёт, интерфейс всё равно покажется).

**Проверка:** отдаваемый HTML содержит `class="app-loading"` с первого кадра; во время
загрузки `body` = `hidden`, после — снят, видны реальные данные. Оба фронта.

**Честно:** сами ~3с загрузки не трогал — теперь это спиннер вместо чужих данных. Ускорение
(объединить `/me`+7 запросов в один) — отдельная задача.

## 6. RLS — изоляция тенантов на уровне БД (главное)

**Запрос владельца:** 10 разных прокатов, «друг друга не видят вообще». До этого изоляция
держалась только на дисциплине кода (каждый запрос обязан писать `WHERE tenant_id`).

**Цель:** Row-Level Security — чтобы **сама база** не отдавала чужие строки, даже если в
коде забудут фильтр.

### Как делал
1. **Слой БД** (`server/db.js`): на каждый авторизованный запрос закрепляю одно соединение
   (`AsyncLocalStorage`) и ставлю `app.tenant_id`. Все `query`/`queryOne` идут через него.
2. **Middleware** (`index.js`): держит контекст на весь запрос (соединение — до конца ответа).
3. **Транзакции** (`orders.js` ×4): переведены с `pool.connect()` на закреплённое соединение.
4. **Bootstrap-пути:** консоль оператора (`admin.js`) — явный обход RLS после проверки
   платформ-админа; регистрация (`auth.js`) — транзакционный контекст для вставки `settings`.
5. **Миграции:** v7 — политики + `ENABLE/FORCE RLS` на таблицах данных (costumes, clients,
   orders, transactions, notifications, settings + дочерние order_* через EXISTS). НЕ трогал
   users/tenants/invites/leads/rate_limits — они нужны до того, как известен тенант (логин).

### Две ловушки (обе критичные — поймал ЭМПИРИЧЕСКИ, не по документации)

**Ловушка 1: пул Neon (pgbouncer, transaction-mode) НЕ держит сессионные переменные.**
Написал стресс-тест: закрепил соединение A с `app.tenant_id='AAA'`, параллельно нагрузил
пул чужими соединениями, перечитывал значение на A.
- POOLED (в проде): **39 из 40** чтений видели чужое значение → RLS бы **тёк**.
- DIRECT (без `-pooler`): **0 из 40**.
- **Решение:** в `db.js` подключаюсь к прямому эндпоинту Neon (убираю `-pooler.` из хоста).
  Строку Railway менять не пришлось.

**Ловушка 2: дефолтная роль Neon `neondb_owner` имеет атрибут `BYPASSRLS`** — политики её
не касаются, и снять атрибут нельзя (нужен superuser; `ALTER ROLE ... NOBYPASSRLS` →
`permission denied`).
- Первый прогон проверки: все контексты видели все 9 заказов. Диагностика показала
  `rolbypassrls=true`.
- **Решение:** миграция v8 — отдельная роль `app_rls` (NOLOGIN, без bypass) + гранты.
  Сервер входит в неё через `SET ROLE app_rls` на каждый запрос (`DISCARD ALL` при возврате
  соединения сбрасывает роль и контекст). Учётные данные/строку подключения менять не пришлось.

### Что сработало (проверено на живой БД)
| Сценарий | Результат |
|---|---|
| Нет контекста → `SELECT count(*) FROM orders` без WHERE | **0** (fail-closed) ✓ |
| Контекст A / B | видит только своё ✓ |
| Вставка чужого `tenant_id` | заблокирована (WITH CHECK) ✓ |
| Оператор (bypass) | видит все прокаты ✓ |
| Приложение под RLS (новый + существующий тенант, полная загрузка страницы) | работает ✓ |

**Порядок деплоя (важно):** сначала выкатил код, который ставит контекст (без политик он
инертен), проверил, что приложение работает; потом применил RLS-миграции; потом снова
проверил. Откат наготове: `db/migration-v7-rls-rollback.sql`.

**Что НЕ проверил напрямую:** аккаунт `skazkaaaaaa` (нет пароля) — но механизм для всех
тенантов один, проверял на эквивалентном «существующем» тенанте (логинится, видит только
своё). Консоль оператора живьём не гонял (нет пароля karnaval) — bypass проверен на уровне БД.

## 9. Полезные команды

```bash
# применить миграцию
node scripts/run-sql.mjs db/migration-vN.sql

# аварийный откат RLS
node scripts/run-sql.mjs db/migration-v7-rls-rollback.sql

# синтаксис
node --check server/db.js

# в базе должны остаться только karnaval и skazkaaaaaa
```

Скрипты (`run-sql.mjs`, чистка тестовых тенантов) идут под `neondb_owner` — у неё bypass RLS,
поэтому она видит все прокаты (это норм для миграций/обслуживания).
